## 一次提交应回答一个问题

Git记录文件内容随时间的变化。工作区是正在编辑的文件，暂存区是准备进入下一次提交的内容，提交是一个带父节点的快照。你可以只暂存一个修改中的部分，让“修复空标题校验”和“改页面颜色”成为两个可分别验证的改动。分支是指向提交的引用，不是复制整个目录。阅读git diff看当前改了什么，git diff --staged看即将提交什么；若只看编辑器，会漏掉新增文件或误带调试输出。写提交说明时描述触发条件和修复后的行为，例如“拒绝全空白标题”，便于未来定位回归。

## 测试从外部行为出发，而不是复述代码

为函数写assert result == expected看似简单，关键是expected来自哪里。若先运行函数再把结果粘成预期，错误实现也可能被永久固定。先根据契约选择正常、边界和失败案例，再观察实现。单元测试隔离一个职责，接口测试穿过路由和校验，端到端测试覆盖真实用户链路；它们发现的问题不同。给临时数据库或假模型是为了控制输入、隔离成本，但假模型测试不能证明真实模型回答正确。一个有价值的失败测试，应能在缺陷版本失败，在修复后通过，而不是只检查某个私有函数被调用几次。

## 从失败信息缩小问题范围

测试失败先分成预期不符、环境失败和测试本身不正确。断言告诉你观察到了什么，调用栈指出错误传播位置。保留最小输入，单独运行目标用例，再检查它依赖的时间、随机数、网络和共享状态。顺序相关的失败通常提示测试污染：前一个用例留下文件、全局变量或数据库记录。使用临时目录和可替换时钟，让每个测试能独立重复。不要靠反复重跑直到变绿来掩盖偶发失败；记录失败比例和条件，才能判断是否属于真正不稳定行为。

## 审查与PR是一种工程沟通

一份可读的PR应让没参与讨论的人知道问题、改动和验证结果。它通常包含触发例子、关键设计取舍、通过的检查与未执行范围。代码审查先看行为和数据边界，再看命名和格式；格式工具负责机械一致性，人负责判断是否满足需求。测试数变多不等于覆盖更完整，仍要检查空输入、权限隔离、重复请求和退出清理。提出改动时标明具体位置与影响，避免只说“这里不好”。合并后记录对应提交，方便把部署版本和测试版本关联起来。

## 在临时仓库练习，而不是试探重要历史

首次学Git可在新建临时目录练习init、add、commit、branch、switch和diff，确认没有重要数据再做练习。撤销已分享的变更通常考虑新增revert提交，保留历史语义；reset会移动引用，是否安全取决于提交是否已共享和工作区内容。遇到冲突，先理解双方想实现什么再合并，不应机械选择ours或theirs。你的验收记录应能指出修改前后的行为、测试命令和提交哈希。若助手写好了代码，你仍需自己读差异、预测测试结果并复做一次，才能把实现证据转成学习证据。

## 标准库unittest验证边界

```python
import unittest

def normalize_title(value):
    title = value.strip()
    if not title:
        raise ValueError("empty title")
    return title

class TitleTests(unittest.TestCase):
    def test_trims_space(self):
        self.assertEqual(normalize_title(" API "), "API")

    def test_rejects_blank(self):
        with self.assertRaises(ValueError):
            normalize_title("  ")

if __name__ == "__main__":
    unittest.main()
```

保存为test_title.py，执行python3 -m unittest -v test_title.py；用例不读取用户文件。

## 失败时检查

### 本地通过CI失败

可能原因：解释器、依赖或工作目录不同

检查：比对版本与命令，使用干净临时环境复现。

### 改动没出现在提交中

可能原因：只编辑了工作区，未暂存目标文件

检查：查看git status与暂存差异。
