# Agent 运行外壳：上下文、记忆与故障恢复

编号：ai-08 · 进阶实践 · 学习预算 8 小时

把一次工具调用扩展为可终止、可恢复的有限任务。

## 学习目标

- 区分对话历史、事实记忆与运行状态
- 设计检查点和恢复规则
- 判断何时需要多Agent

建议先修：[ai-07](ai-07.md)

## 上下文装配决定模型当下看见什么

运行外壳也称harness，它负责把系统约束、用户目标、工具说明、历史观察与当前证据组合成输入，并管理循环和埋点。上下文不是越长越好：重复工具说明、无关历史和原始长日志会挤占有效信息，还可能让模型把旧错误当作当前事实。可以按任务优先级分配预算，保留目标、已确认事实和未完成步骤，将较长日志存成可检索记录。摘要也会出错，应保留原记录ID并允许回查；不能把模型总结的猜测提升为已经验证的事实。

## 三类记忆应该采用不同生命周期

短期对话帮助理解当前请求的指代，长期记忆保存用户确认的偏好或跨任务事实，任务状态记录哪些步骤已执行及其结果。向量记忆只是一种检索方式，不保证取回的信息最新、准确或有权限。每条长期记忆最好带来源、主体、更新时间和失效条件；一位用户纠正了旧信息时，要能更新或撤销。任务状态不宜只藏在自然语言摘要里，否则恢复时很难区分“计划创建工单”和“已创建工单”。把可执行状态保存为结构化字段，再把必要摘要传给模型。

## 检查点保存的是恢复依据

一个任务执行到工具调用前后，需要记录步骤ID、参数摘要、调用结果、状态与外部业务ID。进程在“工具已成功、状态尚未写盘”之间崩溃时，恢复程序不能盲目再写一次，应先用幂等键或外部ID查询确认。数据库事务无法自动覆盖远程系统的全部动作，所以需要明确补偿、重查或人工处理路径。错误分类也很重要：临时连接故障可以有限重试，缺少用户输入应暂停等待，权限不足应停止。恢复成功意味着从已知状态继续，而不是重新从头让模型猜一次。

## 并行与多Agent增加了协调成本

独立只读查询可以并行，彼此依赖的写操作仍需顺序与一致性保护。多个Agent可能分别检索、提取与核验，但也会带来重复请求、不同结论和更高用量。先定义每个角色的输入输出、共享状态归属和汇总规则；两个模型都同意不等于事实验证，因为它们可能共享相同错误来源。工作流能够把固定步骤写清时，先使用工作流；只有明确需要不同上下文或专长分工时，再比较多Agent是否提高任务成功率。评价必须包含协调耗时与失败，而不是只统计并行部分节省的时间。

## 观测与终止属于运行时功能

为一次任务关联trace_id，在每一步记录状态变化、工具名、耗时、用量和错误摘要。取消标记在新步骤前检查，总时限控制整个任务，最大步数避免模型重复循环。用户恢复一个旧会话时，还要检查数据版本和权限是否变化，不能沿用失效的授权。tRPC-Agent-Go等框架提供运行、状态和观测相关组件，可用来阅读成熟组织方式，但接入框架不能替你定义业务恢复语义。本课先用一张状态表推演三种崩溃位置，再考虑框架代码，可减少被库名掩盖的逻辑漏洞。

## 本课具体例子

```python
states = {
 "queued": {"running", "cancelled"},
 "running": {"waiting_input", "completed", "failed", "cancelled"},
 "waiting_input": {"running", "cancelled"},
 "completed": set(), "failed": set(), "cancelled": set()
}
def transition(current, target):
    if target not in states[current]:
        raise ValueError("invalid transition")
    return target
print(transition("running", "waiting_input"))
```

Python 3标准库教学状态机；不包含持久化或真正的异步工作流。

配套实验：[labs/ai_tools.py](../labs/ai_tools.py)。请在解压包根目录按脚本说明运行。

## 本课只做一个任务

为“查询资料后创建工单”设计一次崩溃恢复表。

1. 画出读取、校验、创建、记录结果四步。
2. 分别在创建前、创建后写记录前、写记录后模拟崩溃。
3. 写明恢复时查询什么、是否重试、怎样避免重复。

- 远程工具成功与本地提交可能不是同一事务。
- 状态表应记录业务ID，不只记录自然语言。

</details>

创建前可以重试；创建后但记录前先通过幂等键查询；记录后复用已完成结果。若外部接口无法查询或幂等，应标记需要人工核对。

</details>

### 验收

- 三个崩溃点都有明确恢复动作
- 没有以模型猜测替代执行状态

## 失败时检查

### 恢复后重复创建对象

可能原因：检查点与副作用没有对应标识

检查：用幂等键和外部ID核查

### 摘要把推测变成事实

可能原因：没有保留来源与确认状态

检查：将确认事实和待验证假设分字段
