# 模型、Token 与上下文：把一次回答拆开

编号：ai-01 · 年底核心 · 学习预算 6 小时

## 一次生成发生了什么

把问题发送给模型之前，文本先经过tokenizer变成整数序列，聊天模板还会插入角色及控制标记。模型读取序列，逐步产生下一项的概率，再按生成策略选取并追加，直到遇到结束标记或长度限制。Transformer中的注意力让一个位置根据其他可见位置的信息更新表示；它不是外部资料库查询，也不会自动判断一句话是否符合公司的最新制度。请求成功只说明程序产生了输出。学习时要同时保留原始消息、模板、模型名称、输出和结束原因，才能区分接口问题与答案问题。

## 预算必须给输出留下位置

字符数与token数没有固定换算率，中文、英文、数字、代码以及不同词表都会改变长度。同一段文本若使用不匹配的tokenizer预估，可能在客户端通过而被服务端拒绝。把窗口设为C时，应把系统约束、历史对话、当前问题、检索片段、模板开销与计划输出一起计算。教学例子中C为4096、输入预算3000、输出上限800，还需保留模板余量；实际值应使用服务的真实模板计数。超长时先删去不相关历史或压缩证据，不能截断最重要的来源却仍承诺有依据。

## 采样控制什么，又不控制什么

温度调整概率分布的尖锐程度，top-p限定累计概率候选集合。降低随机性通常有利于固定任务的比较，但temperature为0也不承诺跨硬件、内核和版本逐字一致。事实准确性、权限和输出合法性不能靠低温替代校验。比较两个提示时，应固定模型版本、输入样本与采样配置，多看错误类别，而不是挑一条更顺眼的回答。多模态模型还可能把图片变成视觉表示；图像分辨率、页数和视觉token都会影响资源，不能直接套用纯文本的长度与耗时经验。

## 提示与示例是一份输入约定

先给出任务、允许使用的依据、输出字段和缺少证据时的行为，再给少量相互区分的例子。Few-shot的价值在于说明边界，例如一个有答案案例和一个应拒答案例；大量近似例子会挤占真实证据空间。复杂任务可以要求简洁的判断依据、引用和可复算步骤，不要求展示隐藏的思维过程。Prompt版本应与评测结果绑定：同样叫v2却没有保存实际内容，就无法解释分数变化。模型生成的“我确认正确”仍是输出，不是验证程序的结论。

## 从选模型转向选满足条件的服务

先定义任务需要的文本、图像、工具调用和上下文能力，再比较质量、延迟、资源、许可与接口兼容性。不要因为同一系列名称相近就假定聊天模板、停止标记和适配器可共用。自建模型有显存与维护成本，API调用要计算实际输入输出用量及重试；价格随提供方调整，报告应记录查询日期和计价口径。当前练习只做预算与提示审阅，之后再用相同测试集比较候选模型。能解释一次失败需要回到哪一层检查，比背下参数名更接近交付能力。

## 本课具体例子

```python
window = 4096
parts = {"system": 180, "history": 600, "question": 80,
         "evidence": 2300, "template_margin": 80}
output_limit = 800
remaining = window - sum(parts.values()) - output_limit
print({"planned_total": window - remaining, "remaining": remaining})
assert remaining >= 0
```

Python 3标准库。这里各项为教学预算，不是对任何模型的实际token计数。

## 失败时检查

### 字符少却超上下文

可能原因：用字符数代替真实token计数

检查：核对模板、视觉输入和服务端usage

### 重复请求仍有差异

可能原因：环境与生成实现可能变化

检查：保存版本和参数后再比较
