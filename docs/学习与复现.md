# 学习与复现：一次完成一个可验证的任务

先在静态页学习，再用 CPU 检查理解软件契约，最后到自己的服务器验证真实模型。公开展示页不会代替你启动 GPU；CI 通过也不能证明模型回答正确。

## 教程地图：按当前卡点选择入口

这一版把“为什么、怎么做、怎么看结果、失败怎么查”分别写进具体章节。建议一次完成一个实验；长篇原理可以在遇到对应现象时回来查。

| 你现在的情况 | 先读哪一章 | 本次要交付什么 |
|---|---|---|
| curl已经成功，但讲不清请求过程 | [系统架构与源码导读](系统架构与源码导读.md) | 自己画的调用链与一条JSON字段解释 |
| 路径、环境、SSH、端口经常弄混 | [服务器部署](服务器部署.md) | 环境清单、首个请求与一次故障定位记录 |
| 想弄懂显存、token和速度 | [推理原理与性能实验](推理原理与性能实验.md) | 有控制变量的请求对照及指标口径 |
| 知识库会回答，但不知道为什么答错 | [RAG链路与质量评测](RAG链路与质量评测.md) | 原文→召回→上下文→引用的证据链 |
| 想开始训练，又担心直接微调太难 | [训练微调与模型交付](训练微调与模型交付.md) | CPU小模型训练、保存与独立重载证据 |
| 想让别人打开自己的成果 | [GitHub发布](GitHub发布.md) | 对应提交的CI结果、公开页面和使用说明 |

### 先辨认三种“完成”

1. **已经有实现**：仓库里存在代码，助手或作者曾运行过检查。
2. **我能独立复现**：换一个干净目录，依照记录得到可核对的结果。
3. **我理解并能处理变化**：换问题、改一个参数或遇到故障时，能先提出预测，再用证据解释结果。

这三种状态分别记录。不要因为第1项已经发生，就跳过第2和第3项。也不需要为了证明努力而重新下载所有模型；复现应有明确变量与验收目标。

每次新建一条自己的记录，分开写这两栏：

| 实现证据 | 学习掌握证据 |
|---|---|
| 请求、配置、版本、实际输出、耗时和失败日志 | 操作前的预期、自己的解释、独立重做结果、排障过程 |

助手完成代码和实验属于实现证据。能够自己复做并解释其中一个失败，才是对应的学习证据。页面中的勾选由你决定，换浏览器或设备前导出记录。

## 每天两小时，怎样安排一个学习单元

下面是一种分配方式，不是完成时间承诺。卡在基础环节时可以连续两天做同一个单元。

| 时间 | 动作 | 留下的内容 |
|---|---|---|
| 前15分钟 | 明确今天唯一的问题，画出自己的预测 | “如果改X，我预计Y变化，因为……” |
| 接着25分钟 | 阅读对应教程与一小段源码 | 3个关键函数或参数，以及各自职责 |
| 接着45分钟 | 执行一个有界实验，保留正常与失败输出 | 命令、参数、原始记录和时间 |
| 接着20分钟 | 对照预期解释结果，只改变一个因素复查 | 一张对照表与可能的混杂因素 |
| 最后15分钟 | 用自己的话总结并写下尚未确定的点 | 学习证据、下一步一个问题 |

更长的学习时间可以拆成两个独立单元。不要一边更换模型、一边修改检索方式、一边增加并发，最后却把所有差异都归因于某一个改动。

### 建议先完成的八个单元

| 顺序 | 核心问题 | 可观察的结束条件 |
|---|---|---|
| 1 | 我的请求经过哪些进程？ | 能从路由追踪到Service、Index、Repository和vLLM |
| 2 | 我连接的是哪台机器和哪个环境？ | 能解释两处回环地址、解释器路径与模型目录 |
| 3 | 什么算模型真的就绪？ | 保存模型清单、短请求、停止和恢复后的状态 |
| 4 | max_tokens和实际生成长度是什么关系？ | 同问题对照，记录实际token、finish_reason与时间 |
| 5 | 片段怎样进入模型？ | 找到召回与上下文不完全相同的原因 |
| 6 | 为什么“有引用”仍可能答错？ | 完成少量dev题的逐句核对与错误归类 |
| 7 | 训练究竟改变了什么？ | 在CPU教学例子中保存权重，换进程重载并核对预测 |
| 8 | 怎样交付给另一个人？ | 对方可依据说明访问演示、识别边界并定位源码 |

完成八个单元，代表你建立了这个项目的工程基础。它不代表已掌握所有云产品、分布式系统或真实客户场景；后续扩展应由你遇到的具体需求决定。

## 练习一：识别静态展示的边界

**任务：** 按根目录 README 构建 `site/index.html` 并打开，找到教学问答，写下它的来源性质和资料版本。判断哪些按钮需要真实服务器，为什么性能页没有实测曲线。

**提示：** 检查页面的离线提示，以及 `web/app.js` 中的 `CAPSTONE_OFFLINE` 分支。不要把保存的 GPU 数值当作当前状态。

**提交证据：** 一张自己打开页面的截图、所选示例的性质标记和一段边界说明。未提供模型实测字段时明确写“没有”，不要自行补造。

<details>
<summary>完成后查看参考解释</summary>

离线构建把公开快照、脚本与样式写入一个 HTML。读取课程和教学问答不需要模型；模型推理、检索计算与真实评测需要服务端。公开包没有真实报告，空白性能状态比编造数值更符合证据。浏览器笔记只在本地保存，GitHub Pages 不提供它们的跨设备同步服务。

</details>

## 练习二：让一个 CPU 检查先失败再恢复

**任务：** 先运行 README 中的 CPU 测试。在临时副本中修改一条原文事实，观察题库校验报错，再恢复。不要为了通过测试把参考答案一并随意改掉。

**提示：** 阅读 `evaluation/test_validate_dataset.py`；原文、清单、期望引文和题库划分需要一致。

**提交证据：** 原本通过、修改后失败、恢复后通过的三段摘要，以及导致失败的具体约束。

<details>
<summary>完成后查看参考解释</summary>

这项练习验证参考证据是否漂移，不需要真实模型。测试中使用临时目录是为了保留正常样本；校验通过说明数据约束成立，不等于 50 个模型回答全部正确。

</details>

## 练习三：沿着一条回答找到原文

**任务：** 从公开快照的教学示例或自己真实运行保存的结果中选一条问答，标清其来源性质，再列出问题、片段、引用和回答中的具体事实。教学示例不能用于证明真实请求成功。

**提示：** 一个相关文件名不能支持该文件里没有出现的说法。复合问题还要检查是否漏掉步骤或条件；资料确实缺失时，说明不足可以是合理回答。

**提交证据：** 一段逐句核对说明，指出至少一个已确认点和一个仍需验证的点。

<details>
<summary>完成后查看参考解释</summary>

HTTP 200、引用 ID 有效、关键词命中与语义正确是不同检查。`supported` 是模型判断加服务规则处理后的状态，不是人工验收标记。比较错误案例时应同时保留原始输出、实际上下文和版本。

</details>

## 练习四：准备一次真实推理请求

**任务：** 在自己有权限使用的服务器上，先记录 GPU 型号、当前显存和计算利用率。确定模型路径与独立环境，再检查服务公布的模型名，最后发送一条短请求。

**提示：** 先阅读 [vLLM GPU 环境说明](https://docs.vllm.ai/en/v0.11.2/getting_started/installation/gpu/) 和 [Hunyuan 模型卡](https://huggingface.co/tencent/Hunyuan-1.8B-Instruct)。`CAPSTONE_MODEL_URL` 包含 `/v1`，模型名和 tokenizer 要与运行中的服务一致。显存预算不是算力配额。

**提交证据：** 运行时版本、模型名、请求、原始响应、当前采样与一条自己解释的指标。没有实际运行就标“未执行”。

<details>
<summary>完成后查看参考解释</summary>

模型文件外置，网页不包含权重。浏览器与模型之间还经过 API、检索和记录层；进程存在也不代表整条请求链路可用。历史 GPU 空闲量不能保证下一次实验资源，遇到不足时先调整自己的任务。

</details>

## 练习五：只改变一个因素做对照

**任务：** 用固定问题与固定模型，选择一个变量：检索方式、是否重排或生成上限。保留两次输入、实际输出、错误和耗时，并解释变化是否符合预期。

**提示：** 相同生成上限不保证实际输出 token 相同；不同计时起点不能直接作速度比较。重排不保证一定更好，需查看真正进入模型的证据。

**提交证据：** 一张两行对照表，以及明确写出的限制。不要用一次请求推导生产并发能力。

<details>
<summary>完成后查看参考解释</summary>

同模型、同问题、同生成设置才能减少混杂。吞吐、延迟、失败率与答案质量应分别报告。已反复使用的测试题属于回归，不能继续宣称是未见验收。

</details>

## 练习六：解释历史训练与当前模型的关系

**任务：** 阅读保留的历史训练源码，区分基座、适配器、保存、重载和推理服务五个环节。解释为什么 Qwen LoRA 不能直接加载到混元。本公开包未提供历史实测报告或曲线，暂不据此判断训练效果。

**提示：** 先查看 `training/common.py` 与 `training/test_training.py` 的数据划分和评分约束。训练集更新参数，验证集辅助选择配置，测试集检查冻结后的结果。不同基座的结构与权重必须匹配。

**提交证据：** 自己画的加载关系图，以及“损失下降是否足以证明业务能力提高”的回答。

<details>
<summary>完成后查看参考解释</summary>

适配器只保存部分增量参数，不能替代完整基座。历史 Qwen 结果不是混元结果；当前推理迁移不等于完成混元微调。若任务基线已经全部答对，损失下降也不能被表述为分类准确率提升。合成四分类任务的表现不能推广为未知真实故障的可靠判断。

</details>

## 发布自己的学习记录

整理经过核对的说明、自己的操作证据和限制，放入公开版允许的内容范围，再手动更新 Pages。不要把原始用户问答、服务器配置或模型二进制直接复制到公开快照。

源码许可证尚未选择；模型、框架和自己的新增内容分别确认来源，参阅 [第三方说明](../THIRD_PARTY_NOTICES.md)。仓库能构建、页面能访问和自己能独立完成实验，是三个需要分别验证的结果。

请复制下面的结构到自己的记录中。示例解释采用“待填写”，没有替你预先写出成绩。原始请求和运行日志放在本地 `evidence/`，公开时另行整理可分享的结论。

```markdown
- 代码提交与资料版本：
- 执行位置与Python环境：
- 模型名称、revision与精度：
- GPU采样时间及本实验使用的卡：
- 输入与生成参数：
- 本次唯一改变的变量：

## 实现证据
- 原始请求文件：
- 原始响应/错误文件：
- 指标、单位和计时起止点：
- 尝试总数、成功数和失败数：
- 输出长度与内容是否相近：

## 分析
- 观察是否支持预测：
- 哪个现象还不能解释：
- 可能的其他影响因素：
- 结论适用于什么条件：

## 学习掌握证据
- 我能独立完成的步骤：
- 我能不用参考资料解释的概念：

- 下次只验证的一个问题：
```

### 让结论具有可核查性

“速度很快”没有说明单位和工作量。更好的表述应指出模型、固定输入、实际输出token、计时范围、成功/失败数以及记录文件。“回答准确率高”也需要题集、样本数、评分规则、逐题判断与限制。

如果只做了两次短请求，结论可以是“这两次请求中观察到的差异”，不能直接写成“系统在生产并发下更稳定”。如果一个配置在失败请求上没有结果，不能只删除失败项再计算漂亮的平均数。

## 学会以后，怎样自测

先合上教程，用自己的话回答。查阅答案之后，再换一个例子验证，不要仅记住这几个句子。

| 自测问题 | 及格证据 |
|---|---|
| 为什么0% GPU利用率时仍占显存？ | 能区分模型驻留与采样时刻计算活动 |
| 为什么设置输出上限64不一定生成64个token？ | 能指出实际usage、结束条件与finish_reason |
| 为什么top_k=5却只给模型3块资料？ | 能定位上下文预算，并比较两组片段 |
| 为什么同一篇文档被引用仍不一定支持答案？ | 能找到具体原句，检查数值、日期和条件 |
| 为什么loss下降不保证测试正确率提高？ | 能区分优化目标与任务评判，提供自己的对照 |
| 为什么旧Qwen适配器不能直接给混元使用？ | 能说明基座、参数结构与版本匹配，而不是只说“品牌不同” |
| 为什么Pages能访问不代表GPU模型可用？ | 能画出静态展示与服务器请求的边界 |

对某一项暂时解释不清楚，可以把它标成“会操作、原理待确认”。这是有用的学习记录，不需要把所有复选框一次勾满。
