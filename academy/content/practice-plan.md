# FDE 实践提升计划与验收标准

计划日期：2026-11-16。目标：2026 年底完成三个核心能力验收，2027 年 1—3 月完成迁移与进阶。

用现有 DocLens 做主要训练项目，复用知识库项目进行后续系统集成。每次只领取一个能独立验证的小任务。课程在遇到问题时按需阅读；本计划替换原有“108 小时课程＋18 小时复习”的时间分配，总量仍为 126 小时，不再额外叠加。

本次交付的是计划、任务规格和验收标准。下面拟新增的分页测试、故障注入工具、盲测和交付脚本尚未实现或执行；现有测试与待补项目分别注明。不能把制定计划记为学习通过。

## 三个阶段目标

| 目标 | 必须留下的证据 | 达标条件 |
|---|---|---|
| 独立修改一个功能 | 需求、实现提交、修改前失败与修改后通过的报告、解释记录 | 完成 DocLens 历史列表的一项独立需求；冻结的验收用例全部通过、原有回归无新增失败；不删除断言或扩大跳过范围；能解释 API、业务、数据访问三层各改了什么 |
| 独立定位并修复一次故障 | 原始现象、假设与验证时间线、根因、修复、回归、清理记录 | 对未提前告知原因的单故障，30 分钟内定位到层次，90 分钟内完成诊断和修复；证据解释因果；同一故障可重现、修复验证连续 3 次通过，正常请求仍成功 |
| 同学按照手册独立跑通 | 固定版本交付包、操作手册、同学原始日志、验收表和遗留问题 | 在约定的干净环境，另一位同学不接受口头或远程代操作指导，按手册完成启动、请求、查记录、导出、重启、恢复和停止；全部必须项通过 |

以上时间是训练目标。超时就记录真实耗时和卡点，补练后重测；不为赶时间绕过校验。网络下载、账号开通、预先约定的 GPU 预约等准备时间单独记录，不事后从不利结果中任意扣除。

“独立”允许查官方资料和自己写的笔记；最终验收期间不让 AI 或同学生成实现、定位根因或代操作。训练时可以求助，但要记录提示等级：L0 无提示；L1 指向概念或文件；L2 给排查步骤；L3 给实现或答案。L1—L3 的结果记为“辅助完成”；至少间隔 48 小时，再用改变输入或条件的等价任务无提示复验，才能记为“独立通过”。不能靠记住同一答案完成复验。

## 一 带自动验收的代码练习

### 为什么选 DocLens 历史列表

当前 `backend/main.py` 的 `GET /api/jobs` 没有分页或状态查询参数，`backend/service.py` 组织列表字段，`backend/repository.py` 的 `jobs(limit=50)` 只限制数量。这是范围清楚、能体现三层分工的小功能，不需要加载模型。

已有基础：`tests/test_doclab.py` 使用临时数据目录、FastAPI TestClient 和 `httpx.MockTransport`，已有完整任务、输入异常、取消、模型错误、上传和导出测试。新增练习复用这些能力，不能把模拟响应结果当作真实 OCR 成绩。

在独立练习副本内按 fde2 的 README 建好 Python 3.12 应用环境后，已有基线命令为：

```bash
.venv-app/bin/python -m pytest tests -q
```

执行前确认所在目录是 DocLens 练习副本、解释器属于该副本。已有服务器工作目录和全局环境不用于制造故障。尚无虚拟环境时，先按 README 安装，不把“找不到解释器”记录为业务测试失败。

### 三个递进任务

| 任务 | 要实现的行为 | 自动验收矩阵 | 建议预算 |
|---|---|---|---:|
| C1 限制历史返回条数 | `GET /api/jobs?limit=3` 最多返回 3 条；默认仍为 50；合法范围 1—50；响应保留 `jobs` 列表 | 默认行为、1、3、50；空库；少于上限；0、51、负数和非整数被拒绝；返回字段不丢失 | 8 小时 |
| C2 稳定分页 | 新增 `offset>=0`，默认 0；按 `created_at DESC, id DESC` 排序；保持不带参数时兼容 | 固定时间戳的同时间任务；第一页与第二页无重复且合并顺序正确；越界为空；负 offset 非法；重启读取不变 | 10 小时 |
| C3 独立迁移任务 | 在已完成分页上新增可选 `status` 筛选；只接受事先冻结的合法状态；先筛选，再排序和分页 | 多状态混合样本；目标状态在前 50 条之外也能查到；筛选与 limit/offset 组合；无匹配；未知状态拒绝；遗漏 status 保持兼容 | 10 小时 |

C1、C2 可分层求助；C3 用于“独立修改一个功能”验收。正式开始前冻结允许的状态值、无效输入响应和响应结构，评测者可以保留未知数据用例，但不能隐藏需求。分页验收使用固定数据快照；offset 分页在并发插入时可能发生位移，不把本任务包装成游标分页的一致性保证。

源码注意事项：状态保存在任务 JSON 中，先验证练习环境的 SQLite JSON 查询能力，再决定如何在数据库中筛选；用“较新 60 条 completed、较旧 3 条 failed”验证筛选先于分页。`Repository.jobs()` 也被启动恢复调用，列表接口参数不能意外改变恢复路径的默认行为。当前恢复只扫描默认返回的 50 条记录，超出范围的历史遗留任务另列待改进项，本轮不能宣称任意数量任务均可恢复。

### 每个任务的操作顺序

1. 用自己的话写出输入、输出、兼容行为和失败条件，画出接口到数据库的调用链。
2. 编写或领取验收测试；先在未修改版本上运行，确认至少一项因缺少目标行为而失败。导入失败、语法错误不算有效的“先失败”证据。
3. 仅实现本次需求，保持 API 校验、业务组织、参数化 SQL 各在对应层。先运行当前用例，再运行整个 CPU 回归。
4. 用另一组数据再运行一次，防止硬编码固定样本；重复查询不应产生额外任务或写入。
5. 保存提交号、环境版本、测试报告、已知限制；用 5 分钟解释为何这样修改、哪些边界没有解决。

自动检查分三层：仓库层检查真实临时 SQLite 的排序与筛选；业务层检查参数和输出字段；API 层检查 HTTP 输入与响应。计划新增专门的历史查询测试文件，并纳入现有 CI，领取练习时再逐项实现。验收不以代码行数或覆盖率百分比代替行为检查。

临时目录用于隔离测试数据，参数化测试用于覆盖输入边界，monkeypatch 用于受控替换依赖。具体机制可对照 [pytest 临时目录](https://docs.pytest.org/en/stable/how-to/tmp_path.html)、[参数化测试](https://docs.pytest.org/en/stable/how-to/parametrize.html) 和 [依赖替换](https://docs.pytest.org/en/stable/how-to/monkeypatch.html)。

### 通过标准

- 冻结的需求用例全部通过，整个既有回归没有新增失败；必须项不得以 skip/xfail 代替通过。
- 不修改参考预期来迎合错误输出，不删除测试，不硬编码题目数据。
- 至少保留一项有效的“旧实现失败、新实现通过”对照。
- C3 在一个 4 小时学习块内争取完成实现与相关测试；首次超时允许辅助练习，独立复验另行计时，不抹掉前次记录。
- 能回答三问：参数在哪一层校验？筛选为什么要在 LIMIT 前？相同时间戳为什么还需要第二排序字段？参考答案在自己作答或求助后提供。

## 二 可重复执行的故障复现实验

### 固定实验方式

使用单独进程、回环随机端口、临时 SQLite 和合成样本；每次只注入一个故障。故障控制器计划提供 `prepare → baseline → inject → verify-failure → repair → verify-recovery → reset` 七个步骤，开始训练时逐项实现，不预先宣称已有命令。

每次记录实验 ID、代码版本、环境、固定样本摘要、注入参数、预期失败、实际结果。清理只处理本次实验自己创建的进程和目录；不关闭共享模型，不更改全局驱动，不通过耗尽真实 GPU 显存制造 OOM。

| 实验 | 可控制的注入方式 | 观察与定位任务 | 修复与重复验收 |
|---|---|---|---|
| F1 模型端点配置错误 | 将测试应用指向临时回环服务上的错误 API 路径，使模型探测返回可重复的 404；不修改真实模型 | 区分应用可访问与下游模型不可用；用配置、请求路径和响应证明错误发生在哪里 | 修正练习配置，模型探测恢复；一个合成任务成功；重置后可再次制造同样故障 |
| F2 下游响应超时 | 让本地模拟服务的生成端点延迟 2 秒，客户端读取超时设为 0.2 秒；同时补一个直接抛 ReadTimeout 的快速契约用例 | 检查超时对象、页面与任务状态及错误记录；区别连接错误与读取超时 | 当前页 failed、后续页不再发送、工作槽位释放；单页任务为 failed，多页含跳过页时可为 cancelled。恢复正常模拟服务后新任务成功；不能仅不断增大超时掩盖问题 |
| F3 HTTP 200 但正文损坏 | 返回固定的非 JSON 正文；变体为缺少 choices 等必要字段 | 说明传输成功为什么不等于业务成功；定位解析与任务失败传播 | 应记录 failed 和可理解错误，不生成虚假的 completed/零耗时；换回合法响应后正常完成；相关回归通过 |
| F4 进程重启后任务遗留 | 在临时数据库放入一个 queued/running 的合成任务，再启动新应用实例；进阶变体才终止自己拥有的练习进程 | 检查启动恢复逻辑、历史查询范围和数据库状态；保留任务 ID 与重启前后记录 | 在当前扫描范围内，遗留任务转为 interrupted，未完成页转为 failed，并保留恢复说明；新任务可成功；数据库中已完成任务不被破坏 |

现有源码已覆盖部分模型错误与启动恢复行为，实验的目标包括验证已有保护。只有证据证明行为违背合同才修改代码；若注入是错误配置，修复配置就是正确动作。正式故障考核会在独立练习分支中使用一个事先验证可复现的变体，不随机破坏现用环境。

超时用例双层验证：MockTransport 抛出异常可检查错误处理，真实回环延迟服务用于检查 HTTP 客户端确实执行超时。只让 MockTransport 的回调 sleep 并不能证明网络超时生效。每次练习设置进程退出上限和 finally 清理，发生异常也释放资源。

### 每次排障的七步

1. 保存用户可见现象、原始输入、错误与时间，不先写结论。
2. 先列两个可能原因，说明各自能被什么观察证实或排除。
3. 按客户端、API、业务、下游、存储分层找证据，每次只改一个条件。
4. 找到最小复现；说明哪个条件导致故障，以及取消该条件后为什么恢复。
5. 执行配置或代码修复；补一条可拦住同类回归的自动检查。
6. 连续三轮从干净状态执行“注入失败—恢复成功”；同时跑正常请求与受影响回归。
7. 重置环境并写一页复盘：影响、时间线、根因、修复、预防和剩余限制。模板见 [故障记录](../templates/07-incident-review.md)。

### 通过标准

- 四种故障均有固定输入、稳定失败条件、成功恢复条件和清理记录，连续三轮均一致。
- 正式考核只给现象和验收要求，不告知故障类型；同学或评测者从已准备的变体中选择一种。
- 30 分钟内定位层次；90 分钟内给出有证据的根因与修复；三轮复验与报告可另留 30 分钟。计时是本计划目标，不是产品性能承诺。
- 修复后的正常请求、错误请求和重启流程都符合合同；不接受“重启后碰巧好了但不知道原因”。
- 如需提示，记为辅助完成，至少 48 小时后换变体复验。

故障记录按响应、恢复和沟通分开，参考 [Google SRE 事件响应](https://sre.google/workbook/incident-response/)；本计划只演练单人小系统，不套用大型团队的全部流程。

## 三 一次完整项目交付演练

### 年底交付范围

交付一个包含历史查询改进的 DocLens 固定版本，让同学完成“一页文档解析—查看任务—查看历史—导出—重启—备份恢复”。这是一个可独立验收的产品范围。两个 GitHub 仓库继续独立，OCR 到 RAG 的自动写入留到进阶，不在年底额外塞入新系统。

同学选择自己有权限使用的机器或账号，不共用个人凭据。CPU 验收使用新的应用环境和空白临时数据目录；真实 OCR 验收可以连接实验室已经准备并获准使用的模型服务。后者属于“应用接入既有模型的交付”，不能宣称从零重建了模型环境。

### 交付前提和时间

- 在 12 月 20 日前约好一位同学，提前确认系统、Python 版本、网络/离线依赖方式、测试账号和可用时间；尚未约到人时不能用自己代替“他人验收”。
- 总预算 28 小时：定义范围和检查资产 4 小时、手册 6 小时、自己在新目录预演 6 小时、同学正式验收 3 小时、修订与再次验收 5 小时、报告和演示 4 小时。
- 正式验收目标：CPU 核心流程 90 分钟内完成，真实 OCR 业务流程在模型已就绪时另留 30 分钟；余下 60 分钟用于记录、恢复与停止确认。硬件、依赖下载和权重准备作为事先登记的前置阶段，仍记录实际耗时。

### 你需要编写的操作手册

1. 项目解决什么问题、交付版本与支持环境。
2. 从哪个地址获取源码或包、如何核对版本与文件摘要。
3. 安装依赖、复制配置模板、填写必要参数；每个参数说明来源与默认值。
4. 启动、健康检查、成功输出示例和失败分支。
5. 提交一个样本、查询任务、检查历史筛选、导出中文结果。
6. 停止、重启、备份和恢复；说明数据保存在哪里。
7. 至少三种常见故障、定位命令、预期结果、恢复步骤。
8. 资源边界、已知限制、未验收项与交接联系方法。

每条命令要说明在哪台机器、哪个目录、使用哪个环境执行。手册不填写个人密码或令牌。模板可从 [验收矩阵](../templates/02-acceptance.md) 和 [交付清单](../templates/09-offline-handover.md) 开始。

### 同学必须完成的验收

| 编号 | 动作 | 必须看到的结果 |
|---|---|---|
| D1 | 获取固定提交并建立新的应用环境 | 版本正确、CPU 回归全部通过，无必过项跳过 |
| D2 | 仅按手册启动应用 | 健康/状态接口和页面可访问，模型就绪状态如实显示 |
| D3 | 运行固定 CPU 业务验收 | 使用明确标记的模拟模型完成任务创建、查询、历史筛选和导出；记录不冒充真实推理 |
| D4 | 提交一个无效输入 | 返回合同规定的错误；不产生残留或假成功任务 |
| D5 | 重启应用并查询记录 | 已完成记录和导出内容仍在，未完成任务符合恢复契约 |
| D6 | 备份并在新数据目录恢复 | 业务记录数、指定 ID 和导出内容一致；恢复后应用可正常查询 |
| D7 | 停止本次应用并清理临时资源 | 自有进程退出、端口释放，数据按手册保留，其他服务不受影响 |
| D8 | 在获准 GPU 窗口做一次真实单页 OCR | 保存请求、真实模型版本、任务 ID、完整输出和耗时；人工对照标题及事先选定的三个字段；不把 completed 或 HTTP 200 当正确率 |

执行顺序为 D1—D6，资源就绪时执行 D8，最后执行 D7。若 D8 在另一预约窗口进行，先重新启动应用并检查模型就绪，完成后再次执行 D7，不能在应用已停止时直接提交请求。

D1—D7 为 CPU 交付必过项。D8 为真实 AI 交付必过项：无可用 GPU、模型未就绪或结果不达预先约定的字段标准时，标为“真实 OCR 验收未通过或未执行”，不把 CPU 成绩提升为真实模型交付。预约下一可用窗口复验，不为了赶日期占满共享 GPU。

备份采用数据库一致性机制，或先正常关闭应用再复制完整数据；不能随意复制正在写入的 SQLite 主文件后就宣称备份成功。恢复验证比较业务数据与内容，不能仅凭“文件存在”通过。

### 盲操作规则

你旁观并记录，不解释遗漏步骤、不替同学输入命令。必须指点才能继续的步骤记为失败项，保留原始记录。修订手册后在新目录重测对应流程和受影响项；最终再完成一次从获取到停止的完整无帮助运行。可邀请同一同学重测，但要记录其已熟悉流程；若换另一位同学，能提供更强的手册可用性证据。

每项记录“通过、失败、未执行”，不得用空白代替失败。年度第三个目标必须有真实同学的操作记录；AI 模拟用户或自己重新安装只能算预演。

## 记录格式与结转规则

- 实现证据：代码或脚本是否存在，哪些自动检查真正执行并通过，哪些未执行。
