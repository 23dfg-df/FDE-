## 权重只是显存的一部分

参数数乘每参数字节数给权重存储粗略下界，十亿参数乘两字节约二十亿字节，换GiB除以2的30次方。运行还有KV缓存、激活、临时张量、框架与图捕获开销；训练还需要梯度和优化器状态。上下文与并发会改变缓存需求，因此文件放得下不证明能启动。整卡占用包含别的进程，报告必须区分整卡、框架分配与进程统计。空间估算应留余量并写假设，最终以实际版本和配置验证。

## 带宽、计算与容量作用不同

处理输入的prefill和逐步输出的decode，对矩阵计算、搬运和缓存的压力不同，瓶颈随模型与批量变化。显存容量决定能放多少，带宽影响搬运速度，计算指标还依赖精度与操作类型。不能用宣传峰值替代业务测量。选卡还看驱动、模型内核、功耗、互联、实际配额与维护条件。某卡显存更大不代表每类请求都更快，比较前需固定任务和目标。本课学选型方法，不给随市场变动的采购排行榜。

## 模型文件到服务还需要生命周期

引擎加载模型与tokenizer，管理排队、生成和返回；业务应用负责参数、权限、规则和记录。vLLM连续批处理能调整运行批次，KV管理减少缓存组织浪费，但不会提供无限容量。保持已有验证版本，在隔离目录尝试变更；OCR与文本环境不可无条件混装。多个实例各需明确设备、端口、就绪与路由，增加实例可能复制权重。启动日志、模型列表与低成本请求共同支撑“可服务”的结论。

## 每个指标都应写计时范围

端到端耗时从客户端发送请求算到约定终点；应明确终点是最后输出token还是完整HTTP响应结束。TTFT表示首个token等待时间，客户端流式测量通常只能记录第一个有效内容块到达，响应头到达或非流式总时间都不是它。单请求输出token除完整耗时包含排队与prefill；整轮总输出token除墙钟才是整体输出吞吐。服务指标另有口径，要核对安装版本、名称与单位。首次和预热后分开，保存实际输入输出数与失败；缺失字段写未知，不拿别的请求平均值补齐。

## TPOT是首token之后的平均每token耗时

TPOT（Time Per Output Token）的单位为秒/token。单次生成输出N个token且N>1时，常用请求级估计为（端到端耗时−TTFT）/（N−1）：它排除等第一个token的时间，再平均后续N−1个token。要求两个时间来自同一请求、同一计时边界，N是该次实际输出token数；若端到端终点为完整响应结束，结果还含尾部传输或收尾开销，应标为客户端估计而非纯内核解码耗时。N≤1时本课程记为不适用，不除零、不把0解释为瞬时生成。SSE一个内容块可能合并多个token，所以相邻块间隔不是逐token间隔；无逐token时间记录时不能声称测得每个token的延迟。完整响应token/s包含首token等待，不能替代TPOT。

## 共享环境也能做完整小实验

启动前查GPU、内存、资源分配与余量，只改一个变量，例如并发1到2。约定请求数、输出上限和停止条件，保存所有失败，结束后查本次进程和释放情况。若吞吐提高但等待变长，按条件报告，不宣称普遍提升。采样最大值不等于瞬时进程峰值，显存规划比例也非硬件隔离。CPU模拟可先验证统计代码，GPU结果另存；实验价值是解释数字及边界，而不是让显存条填满。

## 区分显存数量与服务并发

假设启动后整卡用了约20GiB，不能据32GiB总量推断剩余12GiB可再承载某个固定用户数。还需要知道缓存预分配、其他进程、每请求上下文、生成长度和引擎调度。vLLM可能提前规划缓存空间，因此“请求结束后显存没明显下降”不必然是泄漏。先观察服务进程是否继续运行、框架是否复用分配，以及后续请求是否稳定。泄漏判断需要同条件长时间趋势和资源归属，不能只比请求前后两张整卡截图。

## 权重下界算术

```python
parameters = 1_000_000_000
weight_gib = parameters * 2 / (1024 ** 3)
print(round(weight_gib, 3))
```

约1.863GiB，仅假设权重下界，不是服务实际显存。

### 并发增加每请求变慢

可能原因：排队与调度竞争

检查：同时看吞吐、等待和失败。
