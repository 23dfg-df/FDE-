# 模型调用工程：超时、流式与结构化输出

编号：ai-02 · 年底核心 · 学习预算 6 小时

把“调用一次能成功”改造成“失败也能解释”的服务客户端。

## 学习目标

- 区分传输成功、完整生成与业务正确
- 设计有上限的重试和超时
- 校验输出字段与引用范围

建议先修：[ai-01](ai-01.md)

## 先写清请求和返回的契约

一个模型客户端至少需要明确目标地址、模型名、消息结构、输出上限、请求标识和超时。认证信息从环境或受控配置注入，不写进代码、截图或日志。HTTP状态表示服务处理的结果，JSON格式表示数据能否解析，业务校验再判断答案是否满足要求。三层不能合并成一个success。比如200响应可能包含被长度截断的半段JSON；合法JSON也可能引用不存在的文档。日志应留下请求ID、模型版本、阶段、耗时和错误类别，正文与凭据只按必要范围处理。

## 超时和重试会改变业务负载

连接超时、读超时和整体截止时间解决不同问题。客户端停止等待，不保证服务器已经停止生成；立即重发可能让两次计算同时运行。对临时网络故障或提供方明确可重试的限流响应，可以使用有限次数、退避与抖动，并尊重Retry-After；参数错误、鉴权错误不应原样循环重试。将最多尝试次数和总等待预算写进配置，保存每次尝试而不是只保留最后一次。涉及工具写入时，还需要稳定请求键及下游幂等保证，否则“网络恢复”可能变成重复创建工单。

## 流式连接不是逐个字符的承诺

流式接口把输出拆成事件传输，网络数据块、事件、token和字符不是同一单位。接收端必须缓存不完整片段，按协议的事件边界解析，处理空内容、错误事件、最终usage和结束标记。首次非空内容到达的时间是客户端首内容延迟的一种定义，不应把收到响应头的时间直接写成首token延迟。只有收齐终止条件后，才能把本次生成标为完整。用户取消后还要关闭连接并记录状态；若服务端不支持真正取消，界面应说明停止等待与停止计算的区别。

## 结构化结果需要第二道检查

可以在提示或服务支持的约束解码中要求JSON，但业务端仍须验证必需字段、类型、长度、枚举及额外字段策略。示例answer必须为字符串、source_ids必须为列表，且每个引用ID来自本次上下文白名单。不要用简单正则从任意文字中捞出一段看似JSON就判为通过。解析失败应保存可排查的错误摘要，按业务约定返回失败或受控修复；修复次数也有限，并分别计时计费。格式校验通过后，答案是否忠实于原文仍需要评测或人工核验。

## 路由与降级也必须遵守合同

多个模型可以提供主备或按任务路由，但不同模型的上下文、输出格式、工具能力和数据边界可能不同。降级到小模型时可以缩短答案或转为只返回检索片段，不能悄悄删除引用要求。将模型选择理由、尝试次数、用量及最终状态放入记录。没有提供方账单时只报告估算，估算使用实际token、明确单价与币种。第一轮先用本地假响应测成功、超时、限流和坏JSON，再发一条真实请求；这样定位客户端逻辑问题时不必反复消耗GPU或付费额度。

## 本课具体例子

```python
import json
payload = json.loads('{"answer":"按通知提交申请","source_ids":["notice-1"]}')
allowed = {"notice-1"}
assert set(payload) == {"answer", "source_ids"}
assert isinstance(payload["answer"], str)
assert isinstance(payload["source_ids"], list)
assert all(isinstance(x, str) and x in allowed for x in payload["source_ids"])
print("schema_and_source_scope_passed")
```

Python 3标准库。仅验证格式和引用ID范围，不验证答案含义。

## 失败时检查

### 200却得到空答案

可能原因：只检查HTTP状态

检查：检查finish_reason、字段及完整结束事件

### 重试后资源翻倍

可能原因：先前请求可能仍在计算

检查：记录尝试ID并核对服务端任务
