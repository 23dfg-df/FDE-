# AI Coding 与工具链：把生成代码变成可交付改动

编号：ai-12 · 进阶实践 · 学习预算 8 小时

用真实需求、代码差异和测试证据管理AI辅助研发。

## 学习目标

- 给编码助手写可验收的小任务
- 审阅代码与依赖变更
- 区分框架、低代码平台和工作流工具

建议先修：[ai-11](ai-11.md)

## 把需求交给助手之前先定义结果

一项可执行开发任务需要说明触发条件、当前行为、期望行为、输入边界和验收方式。例如“重复导入同一页不创建第二份文档，并返回原ID”比“提高系统智能化程度”更容易实现和验证。补充应复用的API、业务和数据层位置，说明不能改动哪些真实服务或数据。给助手足够上下文，但不把真实凭据和无关客户材料一起发送。先要求定位与最小修改，再看差异和测试；大需求可以有整体方案，实际提交仍以能够独立验证的变化为单位。

## 生成完成和审阅完成是两件事

阅读diff时先看业务条件是否正确，再看异常、权限、持久化和并发边界。助手写的测试可能只复述实现，应至少加入一个能推翻错误实现的案例。依赖更新要核对理由、版本与锁文件，避免解决一个小问题却改变全部运行环境。运行测试时记录命令、环境、通过与未执行项，失败先保留可复现输入。若生成的日志包含令牌、测试会写入真实数据库或脚本自动占用全部GPU，应在执行前调整为隔离样本和明确预算。自动化提高速度，责任仍需要可追踪的人工判断。

## 不同工具在流程中承担不同职责

CodeBuddy等编码工具可嵌入IDE或命令行帮助理解、修改与审阅代码；WorkBuddy相关工作流可用于资料整理或任务协作。具体账号能力、Connector和部署权限要按当前产品与组织设置确认，不能把一个产品的配置路径套到另一个。官方Skill文档把说明与配套资源组织起来，适合沉淀可重复任务。课程只要求用自己已获准的工具完成一个小改动，不要求购买所有产品。记录助手产出、人工修改和最终验收，才能说明工具帮你完成了什么以及你真正理解了什么。

## 框架和低代码平台从维护成本选择

Haystack、LangChain、LlamaIndex可以作为组件和数据链路的参考，Dify等平台提供另一种工作流组织方式。选择时先比较是否能接现有模型、保留来源、导出配置、处理失败、限制权限以及满足部署条件。可视化节点更易沟通，不代表底层调用无需测试；编程灵活也不等于每个组件都值得自己重写。针对同一个只读任务画出两种实现，估算新增依赖和维护责任，再选择一个深入复现。许可证、数据流向和升级兼容属于交付条件，不能仅凭界面或流行度决定。

## 把一次改动沉淀为可复用资产

完成后提交简短问题说明、设计取舍、代码差异、测试证据、运行方法和已知限制。把遇到的真实故障写成“症状—最小复现—原因—修复—回归”的记录，避免只保存聊天过程。需要Skill时，从已经成功重复过的步骤提炼触发条件、输入、依赖、输出及停止条件，不把尚未验证的想法写成自动执行规则。学习者随后应独立修改一个边界条件并解释失败，作为掌握证据。一个整洁的仓库可以展示成果，但能读懂请求链、复现问题和说明限制才让成果在交付中有持续价值。

## 本课具体例子

```python
task = {
 "problem": "Repeated import creates duplicate documents",
 "expected": "Same source version returns the existing document id",
 "acceptance": ["same content twice creates one record",
                "same key with different content reports a conflict"],
 "evidence": {"tests": "not_run", "independent_explanation": "pending"}
}
print(task["acceptance"])
```

标准库任务规格示意，测试状态是待执行，不假称实现完成。

## 本课只做一个任务

把已有项目的一项小缺陷写成可交给编码助手的任务，并设计反例。

1. 选择一个真实可观察行为，写预期和边界。
2. 限定修改范围、运行环境及验收命令。
3. 提出一个错误实现也可能通过的浅测试，再补一个真正能识别错误的反例。

### 验收

- 需求包含触发条件与验收
- 有一个能识别错误实现的反例
- 实现与学习证据分别填写

需要保存：保存本课输入、运行或审阅结果、你的解释与尚未解决的问题。

## 失败时检查

### 助手声称通过但无法复现

可能原因：没保存命令、环境或输入

检查：从最小样本重跑并核对日志

### 一个小修复引入大量新依赖

可能原因：没有限定范围和审阅diff

检查：逐项解释新增依赖，撤销无关改动

## 证据记录

- 实现证据：命令、输入、预期、实际结果、失败与未执行项。
- 学习掌握证据：自己能够解释、独立重做或定位的问题；不能用助手完成替代。

## 官方来源与延伸阅读

- [CodeBuddy：Skills官方文档](https://www.codebuddy.cn/docs/ide/Features/Skills)：理解任务说明、脚本与参考资料的模块化封装。 建议先读：阅读Skill结构及加载方式，核对本机产品版本。（核对 2026-11-16）
- [WorkBuddy Enterprise：产品简介](https://cloud.tencent.com/document/product/1831/134342)：将办公协作和代码研发工具放回需求与交付流程。 建议先读：先确认产品形态，再看本机可用能力与组织授权。（核对 2026-11-16）
- [langgenius / Dify](https://github.com/langgenius/dify)：对比低代码工作流与可编程后端的交付边界。 建议先读：从README和部署说明了解组件，再检查自定义扩展方式。（核对 2026-11-16）
- [langchain-ai / langchain](https://github.com/langchain-ai/langchain)：作为模型应用组件与集成的比较阅读。 建议先读：先核对版本，再从一个最小示例追踪模型调用和状态。（核对 2026-11-16）
- [run-llama / llama_index](https://github.com/run-llama/llama_index)：作为数据接入与检索组件的比较阅读。 建议先读：重点查看数据加载、索引和检索的最小示例。（核对 2026-11-16）
